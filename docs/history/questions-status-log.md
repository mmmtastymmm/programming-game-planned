**Status 2026-07-27 (M16 rethink, latest): Q122 and Q123 ANSWERED — the XP
model is fully specified.** Each track carries **its own `curve_base`**
(`curve_base = dedicated_rate × target_ticks_to_L5 / 15`), with a deliberate
two-tier pacing: a dedicated specialist reaches L5 in ~10 minutes on a JOB
track, ~50 minutes on an AMBIENT one. That gap is what lets the skill route
to a tool licence beat the seniority clock. **Age drops to 0.2 deci/tick.**
Upkeep takes the same bounded hyperbolic as the perks, and its module term
re-bases on installed tools. Two corrections went in with this: the original
Q123 claim that the skill route was "dead on arrival" was true in deci/tick
but **false in levels** (the mean over ten tracks, several at zero, very
nearly cancels the passive lead — a pure miner comes out tied); and
**specialisation dissolves the duty-cycle problem by itself**, which is why
"pay the loop, not the verb" was rejected as unnecessary. **THE BOARD IS CLEAR** — every numbered question through Q123 is decided.

**Status 2026-07-27 (M16 rethink, earlier): Q121 ANSWERED — tools carry the
power, levels license.** Perks take three shapes: tools hold the step
changes (which is what makes an uncapped ladder harmless by construction),
sparse **milestones** at named levels carry qualitative growth (the L3
thresholds that already exist are the model), and genuinely continuous
perks use a bounded integer **hyperbolic**, `max × level / (level + K)` —
which also settles the sensor problem, since `+1/level` switched fog of war
off at a reachable level on a 34×20 map. **Learning is retired entirely**,
perk and track: it was defined as 10% of every other award, and the
mean-across-tracks total level measures that from the same data without a
stored copy. **Ten tracks remain.** Newly open: **Q123** — the passive
tracks currently out-earn the active ones (Age climbs ~7× faster than
Mining), so total level is a clock and the skill route to a tool licence is
dead on arrival; incomes need rebalancing before specialisation means
anything.

**2026-07-26 (sweep, evening): creeping is an argument — answers Q103, implemented the same day.** Neither of the two things the docs said was true: docs/02 and docs/05 called creeping *emergent* ("move in bursts, freeze often") while the verb index promised a `creep` builtin, and the codebase had neither. Investigating showed the emergent claim was **doubly** unworkable. First, it was never expressible: `move_to` blocks until arrival and Pyrite has no position literals (Q80), so *move-a-little-then-freeze toward a target* cannot be written — the closest a program can get is `wander()` + `wait()`, which creeps in a random direction. Second, even granted the ability it would not have worked: detection is a **per-tick geometric check**, so a static listener (Sentry Post, Lantern, a stationary guard) catches an intermittent mover on its first moving tick in range — docs/05 says as much in its own Sentry line. And nothing a bot *did* touched stealth at all: `signature_for` returned exactly `−(Hiding level)`, so the game had stealth states but no stealth play. The ruling: **`creep=True` is a trailing argument on every pathing builtin** (`move_to`, `wander`, `explore`), not a verb — much slower steps (`creep_step_pct`) bought with a **signature cut** (`creep_signature`), which shrinks the *radius* at which the bot is audible instead of the fraction of ticks it makes noise. That is what makes it work against static listeners, and it is unreproducible from existing verbs since signature is unreachable from code. Being an argument rather than a verb also means it composes for free — `explore(creep=True)` is a scout that surveys without announcing itself — and it ships free with its verbs (Q96's rule). Sight is untouched (Q74: sight is absolute), heard-at still floors at 1, and the cut stacks with Hiding levels, Ford quieting, and Snow's mute; engine walks never creep. Implementation note worth keeping: the creep state is stamped as a **timestamp** (`crept_tick`), the twin of `moved_tick`, because the arrival step finishes the action *before* perception runs — a flag read off the live action left the last step of every sneak at full volume, which the tests caught. ⚠HASH (the action/request hash carries the flag; golden regenerated). **2026-07-26 (sweep, night): capability slots — answers Q105, and supersedes Q66's generic module slots.** The audit found the gap was far wider than the question claimed: `grep "tool"` over the whole action layer returns **nothing**. No verb checks any tool, the module catalog holds two entries (`optics` and the inert `backup_core`), printed bots get no modules at all, and `Resource::tool_tier()` — the full 0–4 ladder docs/03 calls *"the arc of the colony: chop, dig, electrify, get rich, get brave"* — is dead data nothing calls. The tool layer was never built, so ungated repair/hijack, instant structures, and instant claim/raze were three symptoms of one absence.

**The ruling replaces generic module slots with per-capability slots, each carrying a bought TIER and an earned LEVEL.** Every bot permanently has one slot per thing it can do — **Mining, Building, Combat, Optics** — so nothing is ever locked out and no rookie trades sight for a drill: gating becomes *tiering*, not permission. The two axes:

- **Tier — bought, at the Upgrade Station.** What the capability CAN reach: mining tier N works resources of tier ≤ N (docs/03's table read literally, at last), and the Station's existing pad/queue/payment-at-mount/coolant flow handles every install (docs/03's Fabricator-makes / Station-swaps split folds into the one pad — two pad flows for one concept earns nothing). **Base tier is 1** for every capability: a fresh print works its whole start zone (Wood, Stone, Sand, Iron, Coal), so the shipped starter program never breaks, and **Copper/Tin at tier 2 is the first upgrade you want — exactly mapgen's midfield expansion band**, so the geography ladder and the tool ladder advance together.
- **Level — earned, by USING that tool.** How WELL the capability performs; this is the existing task-track XP (Mining/Building/Combat/Scouting), whose perks already read as proficiency (+10% yield, +10% build rate, +5% damage, +1 sensor per level). **A tier change effectively resets the level — by ARITHMETIC, not by a reset branch** (refined 2026-07-26): each tier multiplies both that capability's **level thresholds and its XP gain** by a tuning factor `M`. The level curve is cumulative 100/300/600/1000/1500, so a *maxed* tier-1 capability holds 1500 XP while tier-2 L1 costs 100·M — any `M > 15` therefore lands an upgraded bot back at level 0 with no special code. Because gain scales with the thresholds, re-climbing costs the **same work** (100 units of ore to reach L1 at any tier): upgrading buys a temporarily worse bot, never a longer grind. `M` is really the *how-much-mastery-carries-over* dial — at 20 a maxed veteran arrives 75% of the way to the new L1, at 100 only 15% — and nothing is ever taken away on paper. This is the ruling's one real drama: a veteran on a tier-1 drill can out-produce a rookie on a tier-2 for a while.

**XP stays monotonic, which is the scaling design's quiet payoff.** An explicit reset would have been a trap: `xp_total()` drives printer selection keys, quirk manifestation thresholds, **and the scrap valve**, which recycles the fleet's lowest-total-XP bot — so zeroing a track would make a freshly-upgraded veteran read as a rookie and put it first in line to be *dismantled*. Because tiers scale rather than reset, no number ever decreases and no parallel "lifetime XP" counter is needed. FOUR places where the scale leaks are ruled (the fourth found while confirming the other three — it is the one that genuinely breaks rather than merely distorts): **(a) quirk manifestation moves to the Age track** — at tier 2 a bot crosses the 300/900 total-XP thresholds in about nine units of ore, which would pop quirks instantly; Age is tier-independent and keeps docs/09's "fresh prints are quirk-free, so reroll-fishing buys nothing" exactly; **(b) Learning's 10% cut is computed on the UNSCALED award**, or a tier-2 bot maxes Learning after ~150 units instead of ~15,000; **(c) total XP becomes tier-weighted rather than seniority-weighted** — a fresh tier-3 bot outranks an ancient tier-1 one — which is **ratified as correct** for both `SelectKey::TotalXp` and the scrap valve: the colony should eat its least-invested machine, not its newest-but-expensive one. **(d) the wreck self-destruct countdown must stop reading total XP.** It is currently `base + (xp_total/1000) × per_100xp_ticks` (docs/02: "~20 s + 1 s per 100 XP" — the veteran's longer rescue window), and under tier scaling that arithmetic runs away: a mid-level tier-3 bot would carry a countdown of hours, so its wreck effectively never expires and the whole rescue-vs-salvage race stops having a clock. The countdown reads **Age** instead — a long-lived bot earns a long warning, which is what the rule always meant, and Age is tier-independent by construction.

**Hauling keeps no tier** — cargo is a body stat, not a tool — so four capabilities pair with four tracks and Hauling stays purely earned.

**Buildings are built by labor** (the other half of Q105): Smelters, Foundries, Archives, Generators, Taps, Upgrade Stations, and Q98's Pump all become blueprints a bot services, exactly like bridges, roads, barricades, and Q97's paint. Construction is finally uniform with the "designation is the player's; labor is code" pillar, and instant placement stops being the odd case out.

Knock-ons: Q66's slot milestones (+1 slot at 1,000/3,000 total XP, live in `xp.ron`) lose their subject and are **cut** — levels now come from use, which was Q66's spirit anyway ("the body grows by living"); the `optics` module becomes optics tier 1; and **Backup Core is left homeless**, which folds into Q100's already-open question about whether inert hardware ships at all. ⚠HASH and milestone-sized; implementation flagged in [TASKS.md](../TASKS.md). **2026-07-26 (sweep, night, later): the inert hardware — answers Q100, and folds compute into Q105's capability model.** Both entries shipped purchasable and doing nothing; they turn out to be different problems that shared only a Gold Chip price tag.

**The Coprocessor is retired; the PROCESSOR becomes a fifth capability.** "Think while an action resolves" was never a hardware feature — it is a *language* one. `move_to()` is an expression that costs cycles to issue and parks the VM until the world answers; a program that runs past it needs that call to return something *immediately*, which makes actions asynchronous and demands handles, awaits, and a story for faults arriving while the program is somewhere else entirely. That is a whole Tier of Pyrite, and it would make "actions block" — the rule the entire cycle-cost economy rests on — conditional on hardware. So **thinking and acting never overlap, permanently**, and docs/01's "(until a later unlock — see Coprocessor)" parenthetical is cut. In its place, **cycles-per-tick becomes a capability with a tier and a level** exactly like Mining or Combat: the tier is bought at the Upgrade Station (what the chassis can run), the level is earned **by executing operations** — a new **Processing** track, the twelfth — and grants more cycles per tick. Compute stops being the one stat you can only buy, and a hard-working bot's brain sharpens with use. Note the loop this creates, deliberately bounded: cycles → operations → Processing XP → cycles is self-reinforcing, held in check by the L5 cap, the quadratic curve, and tier scaling (a tier-N processor needs `M^(N-1)`× the XP). The other Station purchases (program memory, variable slots, stack depth, log buffer) stay flat, slot-free buys — they are capacities, not things a bot *does*.

**The Backup Core preserves TIERS and wipes XP.** This lands exactly on the seam Q105 cut: the Core protects **what you bought**, never **what you earned**. A reprint inherits every capability tier the dead bot held — so the player never re-buys the hardware, and the replacement is immediately able to work high-tier veins with high-tier tools — while all XP is wiped, so the machine must earn its proficiency back from zero. Death keeps its sting (pillar 3: the *experience* is gone) without costing the colony its material investment twice. It also dissolves the "50% of what?" ambiguity that tier-scaled XP had introduced into the old "preserves 50% XP" wording: there is no fraction to interpret, and no risk of a scaled number turning a consolation prize into a jackpot. Because tiers survive, the Core preserves itself — bought once, it keeps re-arming, which suits a late, expensive, Gold-Chip-priced insurance policy.

One implementation detail remains open and is flagged in [TASKS.md](../TASKS.md), not ruled here: **how the preserved tiers travel from the destroyed bot to the reprint**. A reprint is a fresh print with an allocation-chosen color and has no channel to a dead bot today. The two candidates are an automatic per-faction banked loadout the next print consumes (frictionless, matching "the player shouldn't have to re-outfit"), or the **Black Box** as the carrier — it already drops on every destruction and is already recoverable by a verb, which would make a veteran's hardware a physical object on the battlefield: yours if you hold the ground, deniable if the enemy takes it. **2026-07-26 (sweep, night, later still): the overlay pipeline — answers Q101.** One flat integer (`cost_overlay_centi`, a surcharge on every charged op) was the entire system, which is why docs/05's overlay table was unbuildable (**Static Wastes** `send`×3, **Loop Desert** loop-iteration×3, **Overclock Field** all-ops−1 + crash-dump×2 all need a *key*), and why five written-up quirks sit in `quirks.ron` behind a "waits on M8's per-bot cost overlays" comment (**Tail-Call Optimized**, **Kernel Bypass**, **Dial-Up**, **Telemetry Enabled**, **Eventual Consistency**). Q75's promise that "per-bot overlays cover perks + quirks" was blocked on the same gap. One mechanism has to serve biomes, quirks, and perks together.

**Overlays are one RULE per key, resolved in a three-layer pipeline.** Effective cost is:

    floor₁( region_rule( tile_rule( base + Σ per-bot deltas ) ) )

— the machine adjusts the price, the ground transforms it, the region transforms that, and the global one-cycle floor applies last. **Per-bot deltas go first deliberately, so terrain AMPLIFIES a bot's quirks**: Dial-Up (`send` +1) in Static Wastes (`send` ×3) pays `(3+1)×3 = 12`, not `9+1 = 10`. That is the point of the choice — a loud radio is *worse* in a jamming field, and quirks get more dramatic rather than more arithmetic. The cost is that overlays cannot be pre-expanded into baked value tables: a `×3` must survive to runtime as a rule. docs/05's anti-stacking guarantee is preserved by restating it one notch up — **within a layer each key has exactly one rule** (a specific row beats a general one: Overclock's crash-dump row wins over its all-ops row), so ambiguity is impossible; what varies is only the bot standing there. The key space already exists: `CostTable`'s named op classes (`statement`, `assign`, `arith`, `compare`, `if_eval`, `loop_iter`, `user_call`, `list_op`, `attr`, `enum_ctor`, `match_base`) plus every builtin by name.

**Forced charges take overlays after all**, reversing M8's "punishments keep fixed figures" exemption — so Overclock Field's doubled crash dump works exactly as written. The exemption existed to prevent a tax spiral, and that worry does not apply: forced charges are **debt** (Q75), executing immediately and driving the budget negative to be repaid later, so they are never affordability-gated and no overlay can strand a bot by making dying expensive.

**`bank_cap` becomes a big constant instead of a per-tile derivation.** Q82 promised it derive per-bot-per-tile from the max effective op cost; that is now unnecessary per-tick work. It is a flat ceiling (~100 cycles) with a **load-time validation** that no overlay can push any *non-forced* op above it — which keeps Q75/Q82's real guarantee ("freeze-forever is impossible") as a checked invariant rather than a runtime computation, and follows the codebase's existing loud-assert-at-load pattern. Banking is also self-limiting in practice: a bot only accumulates while paused in front of an op it cannot yet afford, and spends the moment it can, so a generous cap never becomes a pacing knob.

**Overlays attach to REGIONS, not tile kinds — but Corruption keeps its tile-based tax, and that is why there are three layers.** Regions are authored areas in the `MapSpec` (a per-tile region index parallel to the terrain grid: deterministic, O(1) lookup, hashed with the map rather than per tick), which lets a biome have any shape and is the natural home for **boss biomes** — a punishing zone around a boss, unrelated to the ground under it. Corruption cannot move to that layer: its tax reads `is_corruption(pos)` and follows the *ground*, and docs/05 rules that killing a Blight Core stops the spread while "the creep it made stays until cleansed" — so a region-scoped tax would vanish with the core and **Cleanse would lose its entire purpose**. Tile-kind rules therefore stay for terrain that carries its own price (Corruption today), regions handle authored biomes, and a tile inside both pays both in pipeline order.

Knock-on: docs/05 promises "the editor shows *effective* per-line costs for the tile the selected bot stands on", which the editor cannot do today (it paints base costs from `pyrite::analysis::line_costs`) — game-crate work that rides along. Implementation flagged in [TASKS.md](../TASKS.md). ([05-terrain.md](../05-terrain.md) Biome cost overlays, [07-architecture.md](../07-architecture.md), [09-quirks.md](../09-quirks.md).)

**2026-07-26 (post-sweep review): eleven same-day rulings, audited — four refinements ratified, two new questions opened.** An xhigh multi-agent review of the day's docs confirmed 15 defects, all doc-level. The dominant class was **incomplete propagation**: each ruling landed in this worksheet and one or two docs while the *owning* doc kept specifying the superseded mechanism, so `bank_cap`, the wreck countdown, quirk manifestation, the Coprocessor, the Backup Core, Optics, and the build-tool gates each had two mutually exclusive specs in the corpus. Those are corrected in place. Four findings were real design holes rather than stale text, and are ruled here as **Q105-R1..R3 and Q101-R1**:

- **Q101-R1 — the load-time `bank_cap` check must evaluate the WORST CASE, not just overlays.** Per-bot deltas apply *inside* the region/tile multipliers, so validating `region(tile(base))` alone certifies a cap that a quirked bot can still exceed: a Dial-Up or Telemetry Enabled bot in a multiplier region could face an op it can never bank for — freeze-forever, reachable only for quirked bots and therefore the hardest case to diagnose. The check evaluates `region(tile(base + the largest cost-raising per-bot delta any quirk or perk can contribute))` for every key. Quirks are data, so the worst case is computable at load.
- **Q105-R1 — a tier's grant must dominate the levels it resets.** The tier×level contract defines a distinct *reach* only for Mining; for Optics, Combat and Building the tier grants the same stat the level does, so tier scaling could make a bought upgrade a **net downgrade**: a Scouting-L5 scout sees 10 tiles, buys Optics tier 2, resets to level 0, and sees ~7 — paying Chips and a Station trip to go blinder. Rule: tier N's flat grant ≥ the L5 bonus of tier N−1, checked at load. Upgrading is then always a dip in *rate of improvement*, never in absolute capability.
- **Q105-R2 — the deleted build-tool gate is replaced by `Building tier ≥ 2`.** Q105 removed tool modules and gave every print Building tier 1, which silently ungated the highest-stakes verbs: a stock rookie could hijack a maxed veteran's wreck or convert a defeated nest. Field repair (wreck rescue), `hijack`, and nest claim/raze now require Building tier ≥ 2; ordinary `build()` and structure `repair()` need only the base tier, so construction never waits on anything. Base weapon damage likewise comes from **Combat tier 1** now that weapon modules are gone.
- **Q105-R3 — the scrap valve and `SelectKey::TotalXp` rank by INVESTMENT, not raw XP.** Q100's Backup Core wipes all XP on exactly the bots carrying the most bought hardware, walking into the trap Q105 rejected an explicit reset to avoid: a Gold-Chip reprint arrives with tier-4 capabilities and zero XP, reads as the fleet's cheapest machine, and the economy valve dismantles the colony's largest hardware investment for a partial refund. Investment = lifetime XP **plus bought capability-tier value**, so "eat the least-invested machine" means what it says.

Two findings are genuine design questions rather than propagation errors, and are opened rather than patched: **Q109** (enemy paint as a remote fault injector) and **Q110** (Tier 0 cannot express a safe attack). The review also confirmed the phase-4 pass assignment was never written down despite being hash-affecting — now specified verb-by-verb in [07-architecture.md](../07-architecture.md), including the consequence that `repair` and `salvage` are both Work, so the wreck race still resolves intra-pass by entity ID.

**2026-07-26 (post-sweep review, later): paint sabotage stands — answers Q109.** Ruled **(d)**: an enemy paint stroke that strands a program color is **legal play**, not a bug to patch, and the fix is the tuning value that was doing most of the damage. Three findings from the investigation drove it. First, **the unreachable-destination fault is not new and is already celebrated** — docs/05 says outright that enemies can "`demolish` **your** bridge — behind your raiding party", which strands bots exactly the same way; adversarial terrain causing no-path faults is an established, deliberate part of the game. Second, **crash-loops are lethal generally, not just here**: any program faulting every loop-around dies on the same clock, and docs/01 frames that as pedagogy ("the punishment is the tutorial"). Third, **the severity was mostly a wrong number**: `tuning.ron` carried `fault_damage: 5` against Q84's spec figure of **2**, so a 40-hp bot died in eight faults (~25 s) rather than twenty (~60 s) — the difference between no chance to react and time to read the crash dumps flooding telemetry. `fault_damage` is now **2** (⚠HASH, golden regenerated).

So paint keeps its full sabotage surface, including the destination tile: painting the ground under a rival's Depot in a color their haulers `avoid=` is a real weapon with three real counters — **repaint it** (3 ticks, the same as they spent), **kill the painter** (they had to stand in your territory to do it), or **stop passing `avoid=` on a critical supply route**. Rejected: **(a)** a final-step exemption (it would only fix the destination case anyway, leaving a painted chokepoint identical, and it carves a special case into Q96's clean impassable-like-water rule); **(c)** pricing or per-tile-cooldown paint (both contradict Q97's material-free ruling, and a cooldown taxes ordinary zoning to punish a rare case). **(b)** — a `try_move_to()` joining the existing `try_deposit`/`try_withdraw`/`try_send` family, returning `False` instead of faulting — is **backlogged, not cut**: it is the right long-term answer for programs that want to be robust against any unreachable goal, but it is opt-in, so it must not be the only thing standing between a new player and a dead colony. ([05-terrain.md](../05-terrain.md) Tile Composition, [TASKS.md](../TASKS.md).)

**2026-07-26 (post-sweep review, last): the premise was false — answers Q110.** The question asked how Tier 0 could express a safe attack, given that binding a target once needs Tier-1 variables. It cannot — **and it never needed to**: docs/06's construct tree runs `START → F_SENSE → IF → F_ATK` with `VAR → IF`, so **`attack` is unreachable without `if`, and `if` is unreachable without Variables**. There is no tier at which a player can attack but not bind. Tier 0 cannot attack at all, so the gap does not exist.

What the investigation *did* find is that the Drone was never a Tier-0 program — it has always used `if exists(enemy):` — so docs/04's "teaches Tier 0" heading was simply wrong (the intent survives and is worth keeping: docs/06 rule 3 has Ferals **preview unlocks**, and the pacing table wants the player to "want `if` because they *felt* its absence"). The heading now says what the Drone actually does.

The real defect was a two-line source bug, now fixed in all four archetypes: **bind the target once**, then walk to it and strike it. Re-querying `closest()` after a blocking `move_to` is a check-then-act race — during the walk the target can die or be displaced by a nearer one, and the second query returns something the bot is not adjacent to, faulting on exactly the range check Q108's `move_to` was added to satisfy. The fix also improves the teaching: the first program a player reads now demonstrates *why variables exist*, which is the next thing docs/06 wants them to reach for.

**One race survives deliberately.** If the bound target dies *during* the walk, `attack(target)` faults on a stale handle, and nothing in the verb set cheaply asks whether a handle is still alive (`is_seen()` distinguishes seen from heard, not living from dead). That is designed friction — docs/01's "the punishment is the tutorial" — with the `on error:` window as the immediate answer. The fault-free form is a **`try_attack()`**, backlogged beside Q109's `try_move_to` so the `try_*` family (`try_deposit`, `try_withdraw`, `try_send`, `try_broadcast`, `try_receive`) grows in one coherent pass rather than two one-offs. Hash note: Feral program text is hashed into the program library, so **any replay containing nests changes hash** — but the golden fixture has `nests: []` and its hash is **unchanged**, verified rather than assumed.
